# NEXUS — build log · 2026-09-14

## Milestone 28 — Files

**Deliverable:** `index.html` now **718,188 bytes** (~701 KB), still one file /
no build step / no dependencies / offline.

Local file references. A file is stored **as its own bytes**: the record carries a
Blob and nothing else that can be computed. Upload (file picker *and* drag-and-drop),
inline preview (image / PDF / text), derived metadata, and real association to tasks,
projects, notes and journal entries. Nothing is uploaded anywhere — the File API
reads a local file and the Blob is stored in the same IndexedDB workspace as
everything else. No server.

### The governing principle

**A file record IS its bytes.** The stored shape is exactly
`{ id, name, label, refs, createdAt, blob }`. Size, mime type, kind and extension are
read off the Blob at render time by `Derive.fileMeta()`; every count, total, byte
sum, percentage and link count is computed from the collection. A record that loses
its Blob is not a file and is dropped rather than rendered as a row that cannot be
opened. This is the M26 finance lesson applied to binary content: the *content* is
the truth and the descriptor is derived, so a file's metadata can never drift from
what the file actually holds.

**Links are derived in both directions.** `Derive.fileRefs(f)` resolves a file's
pointers to real records (a dangling pointer is kept and flagged `missing`, the same
rule notes and inbox captures follow). `Derive.filesFor(type, id)` is the inverse —
which files point at a record — computed by scanning the collection, so the two sides
can never disagree. Nothing is kept in sync.

**One path creates a file.** `FilesPage.attachTo(type, id, files)` stores the bytes
and points the new record at the record in one step. The Files page and the task
detail panel both go through it, so a file created from either place is an ordinary
file.

### Data-model changes

- **DB version 2**, adding the `files` object store. The upgrade handler creates only
  the stores that are missing, so an existing workspace keeps every record it had.
- `Repo.map` gains `files: 'files'`; `normalizeFile` was rewritten to carry the Blob
  and to **stop storing `type` and `size`** — both are derived now.
- `DEMO_FILES` produces flat records (`{ id, name, label, refs, minutesAgo, blob }`);
  the demo content is real text and real SVG, so every demo file opens.
- `Derive` gains `fileSize`, `fileMeta`, `fileRefs`, `filesFor`, `filesSorted`,
  `fileKindRows`, `fileStats`, `fileSearch`, `filesList` (the only shape the page
  reads). `FILE_KIND_META` is one list driving the row badge, the kind filter and the
  storage breakdown, so a kind cannot exist in `fileKind()` and be missing from the UI.
- `State` gains `fileById`, `addFile`, `updateFile`, `deleteFile`, `addFileRef`,
  `removeFileRef` and the `files` getter/setter.
- **The connection is bidirectional.** `TaskDetail` now shows a `Files · n` section
  listing the task's attachments (derived via `filesFor`), attaches new ones through
  the same `attachTo`, and opens one in Files. The Files preview panel follows a
  pointer back to the record: tasks, projects, notes and journal entries all open.

### Bugs found and fixed

1. **The demo files were written to the database but never reached the live state.**
   On a first run the page showed **0 files** while IndexedDB held all six. Root cause:
   a Blob cannot survive `JSON.stringify`, so the demo files cannot live in `DEMO` —
   and `_reconcile()` builds its fallback from `DEMO`. Every other collection falls
   back to `base[coll]`; `files` had no fallback at all, so `State.data.files` stayed
   `[]` after seeding even though `Repo.seed()` had persisted the records. Fixed by
   making `DEMO_FILES` the fallback inside `_reconcile`, applied under **exactly the
   same rule as every other collection** — only when the collection was never hydrated
   — so an emptied workspace still keeps its emptiness across a reload. The general
   lesson: *a collection whose demo fallback cannot be expressed in `DEMO` needs its
   own fallback at the same point, or the seed writes data the UI never sees.*
2. **`Derive.money` was already correct; `t28` was not.** The regression sweep failed
   one check — "the per-day figure is formatted to paise" — reporting `₹1,616.43`.
   That figure is *correct*: `financeMonth().avgPerDay` divides by **elapsed** days,
   and the demo spends ₹22,630 in September, so 22630 ÷ 13 = ₹1,740.77 on 13 Sep and
   22630 ÷ 14 = ₹1,616.43 on the 14th. The assertion had hardcoded `'₹1,740.77'` — a
   date-dependent demo value. **A stale test, not an app defect.** Fixed to assert the
   guarantee the milestone actually makes (rounded to paise, never a raw division
   tail) instead of a frozen number. Same family as M27's `overCount` and contrast
   lessons: assert the property, never the demo's current value.

## Milestone 29 — Search

**Deliverable:** `index.html` now **748,531 bytes** (~731 KB), still one file /
no build step / no dependencies / offline.

One query across **every** collection the workspace holds — 204 records across 11
kinds: tasks, projects, goals, notes, journal, inbox, finance, files, habits, the
calendar and the activity log. Results are ranked, grouped by kind, and every hit
opens the record it names. Reached from the command palette, which carries the query
across.

### The governing principle

**The index is built, never cached.** `Derive.searchIndex()` reads every collection
on every call, so a record you just changed is already searchable and a deleted one
is already gone — the results can never describe a workspace that no longer exists.
Caching an index is the same class of bug as storing a derived value; it just drifts
in memory instead of on disk.

**The ranking is a rule, not a heuristic.** A term scores by the strongest field it
lands in — a name at the start 160, inside a name 100, the record's structured
context 50, its long text 25 — and **every** term must land somewhere, so a two-word
query means both words are present. Groups are ordered by their best hit, ties broken
by the canonical kind order, so the same query always produces the same list.

**A result says why it matched, once.** The snippet carries the matched context (a
window around the first real match, with `…` when clipped); the meta line carries the
record's own figures. Where the two would say the same thing, one of them is noise.

### Data-model changes

- No new collection, and nothing new is stored. Search reads what is already there.
- `SEARCH_SOURCES` — one vocabulary driving the scope chips, the group headers, the
  aside's index and the tie-break order, so a source cannot exist in the indexer and
  be missing from the UI.
- `RECORD_ROUTES` + `revealRecord(type, id)` — one shared "open this record", now used
  by the Files panel, the search results **and** the palette. `FilesPage._gotoRef` is
  a one-line wrapper around it, so "open this record" means the same thing everywhere.
- `Derive` gains `searchIndex`, `searchScore`, `searchSnippet`, `searchRecent`,
  `searchBrowse` and `searchAll` (the only shape the page reads).
- `SearchPage` + the `search` route. **No `NAV` entry** — the reference sidebar has no
  Search item, so the route is registered in `boot()` and reached from the palette.
- The palette's stubbed *"Universal search arrives in a later milestone"* action is
  gone: it opens the real page, files are now indexed, and any non-empty query
  prepends a `Search everything for “q”` row so the palette never dead-ends.

### Bugs found and fixed

1. **A result quoted itself in lower case.** `searchIndex` folded `secondary` in place,
   so a hit whose snippet fell back to that field read `"racing game"` instead of
   `"Racing Game"`. **Found by looking at a screenshot** — every arithmetic assertion
   passed. Fixed by keeping each weighted field in its original case and folding it
   once into a `*Lower` companion; that also stops a long journal entry being re-folded
   for every word of the query.
2. **`Page.navigate` to the identical URL does not reload.** Writing t30's "a reload
   starts the Search page clean" check exposed it: the document was never torn down, so
   in-memory state survived and the assertion was meaningless. Verified empirically with
   a probe global — from `…index.html#journal`, navigating to `…index.html` **reloads**,
   to `…index.html#journal` **does not**. t29's and t30's reload helpers were passing
   vacuously; both now bounce through `about:blank`. I then checked every older suite:
   t8–t20 use `Page.reload` and t21–t28 navigate to the bare URL, so all of those were
   genuine. The trap is now recorded in the skill.
3. **The palette's search command was unreachable by sight.** "Search everything" is
   the tenth action and the palette's default view shows the first nine, so the command
   existed but could not be seen. It is reachable by typing, which is what the suite now
   asserts — plus that the command really exists in the full list.
4. **A wrong test expectation, not an app defect.** The live-index check assumed adding
   a task grows the index by exactly one. It grows by two: creating a task also writes
   an activity entry, and that entry is searchable too. The cascade is correct; the
   check now asserts on the record rather than on the size of the whole index.

## Milestone 30 — Activity

**Deliverable:** `index.html` now **776,427 bytes** (~758 KB), still one file /
no build step / no dependencies / offline.

The log every mutation has been appending to since M13 is finally readable: 20 demo
entries across 7 days and 11 kinds, grouped by day, filtered by kind and by range,
searchable, with per-kind counts and a real summary. This milestone is as much a
**correction** as a feature.

### The governing principle

**A relative age is a derivation, never a stored string.** Every activity entry used
to store its own age — literally `at: 'Just now'` — written at 27 call sites. The
consequence was invisible for seventeen milestones: an entry written yesterday still
claimed to be just now, and the log could not be grouped by day at all, because it
held no real time. Age is computable from a timestamp, so the log now stores a real
`createdAt` and `Derive.activityTime()` renders it. Legacy `'2h ago'` / `'Yesterday'`
tokens are resolved **once** at hydrate and then persisted, exactly like a demo
event's `dayOffset` — never re-anchored on the next load.

**Everything the page shows is derived.** The day an entry belongs to, the per-kind
counts, the day grouping, today / this-week / span / busiest-day — all computed from
those timestamps. The stored entry is exactly `id · kind · text · createdAt`, and the
suite asserts that key set directly.

### Data-model changes

- `normalizeActivity(a)` — coerces any record into `{ id, kind, text, createdAt }`,
  migrating a legacy age token once. An unknown kind falls back to a documented
  `other` bucket rather than being kept as-is.
- `ACTIVITY_KINDS` — one vocabulary (11 kinds + the fallback) driving the filter
  chips, the row icons and colours, and the aside's breakdown, so a kind cannot exist
  in the log and be missing from the UI.
- The demo log grew from 4 entries to 20, anchored with `hoursAgo` / `daysAgo` so the
  timeline has real days to group by.
- `Derive` gains `activityTime`, `activityDay`, `activitySorted`, `activityCounts`,
  `activitySearch`, `activityRange`, `activityRows`, `activityDays`, `activityStats`
  and `activityList` (the only shape the page reads). `activityList` also returns
  `baseCounts` — the per-kind tally inside the current range and search but before the
  kind filter — so a chip counts what selecting it would actually show.
- `State.clearActivity()`, and `ActivityPage` with the `activity` route (which was in
  `NAV` all along, so it stops being a stub).
- The dashboard's Recent Activity feed now uses the vocabulary for its icon and the
  derived age for its timestamp, and TaskDetail's trail reads the derived age too.

### Bugs found and fixed

1. **The log stored its own age, so it never aged.** 27 call sites each wrote
   `at: 'Just now'`. The tell was that the Activity page could not exist at all: with
   no real timestamps there is nothing to group by. Fixed by storing `createdAt` and
   deriving the string. **The cheapest proof this cannot regress is asserting the
   entry's key set exactly** — the same technique M28 used for file records.
2. **The fix was one substitution, not 27 edits.** All 27 call sites ended in the
   identical fragment `at: 'Just now'`, so a single global replace corrected every one
   — verified afterwards by grepping that no occurrence remained. Worth remembering
   the next time a write path is mechanically duplicated: reach for one replace, not
   an editor per call site.
3. **The empty state was unreachable.** The demo seeds a log and nothing could empty
   it, so the "honest empty state" would have been dead code that no user could ever
   see. The page grew a confirmed **Clear the log**. Nothing is logged about the clear
   itself — an entry describing it would instantly refill the log the user just
   emptied — and the suite proves the clear touches no other collection.
4. **A test bug, not an app defect (×5).** Five checks failed on the first run: two
   were a name collision (`j.rows` was already a count, so `j.rows.length` was
   `undefined`), and three compared against a total captured *before* the cascade
   test appended an entry. Both are the "derive the expectation from live state"
   discipline — the stale capture was the same mistake as a hardcoded demo count.

## Milestone 31 — Analytics

**Deliverable:** `index.html` now **813,182 bytes** (~794 KB), still one file /
no build step / no dependencies / offline.

The last `Life` stub, and the milestone the component system was already waiting for:
`.chart-bars`, `.heat`, `.donut` and `.chart-line` had been defined since M6 and used
almost nowhere. Four views — **Overview · Momentum · Focus · Money** — over nine
weeks, thirty days, four weeks and six months respectively.

### The governing principle

**Nothing is stored for analytics and nothing is estimated.** Every bar, rate and
average is a fold over real records inside a real date range. `periodFigures(days)` is
the ONE place a period becomes figures, so a finished week, a week in progress and
*the same days of last week* are all measured by exactly the same rule.

**A period in progress is compared like-for-like.** The first cut compared the current
week against the whole previous week. It ran on a Monday, so every metric read as a
collapse — −5 tasks, −720 focus minutes, −29% habits — all of it technically true and
all of it meaningless. The comparison is now week-to-date against the same number of
days of the week before, and the suite asserts the *relation*
(`deltas === current − previousToDate`) rather than a number.

### Data-model changes

- Demo done-tasks gained a `doneDaysAgo` anchor, resolved **once** in `normalizeTask`
  into a real `completedAt` (the same pattern as a demo event's `dayOffset`, the
  activity log's `hoursAgo` and a journal entry's `dayOffset`). Without it a completion
  trend had no dates to draw at all.
- `Derive` gains `weekStart`, `weekLabel`, `periodFigures`, `weekSeries`,
  `focusWeekday`, `activityHeat` and `analyticsList` (the only shape the page reads).
- `AnalyticsPage` with the `analytics` route, and no new storage of any kind.

### Bugs found and fixed

1. **The week comparison was unfair, not wrong.** Comparing a one-day-old week against
   a finished seven-day week produced five alarming deltas that were all true and all
   meaningless. Fixed with `periodFigures` + a `previousToDate` window of exactly
   `current.dayCount` days. **Whenever a figure compares two periods, ask whether they
   are the same length.**
2. **`x || default` silently swallowed a legitimate zero.** `focusWeekday(days)` was
   written `this.focusRange(days || 28)`, so `focusWeekday(0)` — an explicit empty
   window — quietly returned a month of data. `weekSeries(0)` and `activityHeat(0)`
   were correct because they use loop bounds, which is exactly what made the
   inconsistency easy to miss. Now `typeof days === 'number' ? days : 28`, with the
   zero case asserted.
3. **A metric tile described two scopes at once.** "Tasks done 9" with "unchanged vs
   last week" underneath pairs an all-time total with a week-over-week delta and reads
   as a contradiction. Each tile now pairs a period total with a period figure, and the
   like-for-like comparison lives in its own card where it can be explained.
4. **Three test bugs, not app defects.** Two Overview assertions ran after the tab loop
   had left Money showing; and one check was written against a helper that did not
   exist. The first is worth remembering: **a loop that switches tabs leaves the last
   one active** — go back before asserting on the first.

## Milestone 34 — NEXUS Score v2

**Deliverable:** `index.html` now **897,982 bytes** (~877 KB), still one file / no build step /
no dependencies / offline.

What looked like a scoring retune turned out to be a **data-model** milestone. The plan was to
replace the stale `due === '12 Sep'` literal in the overdue term and lift the demo's ~48/100.
But the stale literal existed at **six call sites**, so "overdue" was broken *app-wide* — in
the task summary, the project and goal rollups, and the score — and no amount of reweighting
could fix a term that could not read a date. So M34 rebuilt how a due date enters and lives in
the workspace, and then rebuilt the score on top of it. The demo workspace now scores a
measured **74/100 with `+1 since yesterday`** over a genuine 14-day history.

### The governing principle

**A due date is a fact about a day, not a label.** The workspace stored `due: 'Today'` and
`due: '12 Sep'` — a *relative* string whose meaning silently changes as the calendar moves, and
which no date comparison can read at all. Worse, `_dueKey` deliberately resolved `"12 Sep"` to
the nearest **future** occurrence, so a due date was structurally incapable of reading as past.
Now one boundary parser, `parseDueToken`, resolves any token to a real `YYYY-MM-DD` day key
**once**, at the edge (a value that is already a key passes straight through), and every record
stores that key. `dueLabel()` turns the key back into words for display. The label is derived;
the day is stored.

**A per-day figure must be computed from what was true on that day, never from a current flag.**
This is the same lesson as M30's `at: 'Just now'` in a new costume, and it was the only bug a
history-stability assertion could catch.

### Data-model changes

- **`Task.due` is now the single due field** — a real day key, or `null`. The legacy `dueDate`
  field is **removed** from the record (the old alias is still honoured on *read*, so nothing
  persisted by an earlier version breaks).
- **`parseDueToken(token)`** — the one boundary parser. Handles a real key (pass-through),
  `Today` / `Tonight` / `6 PM` / `Tomorrow` / `Yesterday`, `this week` / `next week`, and
  `"12 Sep"` (month lookup, nearest not-yet-passed). Unparseable → `null`, never a guess.
- **Demo tasks carry relative anchors** (`dueDaysAgo`, `createdDaysAgo`), resolved **once** at
  hydrate and then persisted as real values. This is what gives the workspace a real three-week
  history instead of a static array.
- **`State.data.scoreHistory` deleted.** It was a static 9-point demo array nothing ever
  appended to, so the sparkline and the delta badge were both fiction.
- **New `Derive` members:** `isOverdue`, `isDueToday`, `overdueTasks`, `dueLabel`, `scoreAt(day)`,
  `scoreHistory(n)`; `nexusScore()` rewritten as a fold over `scoreAt`.
- **No DB bump.** The shape of a task changed but no store was added, so the schema version did
  not move; the read-side alias covers old rows.

### The score, redefined

Every term was redefined to measure what its label claims, rather than reweighted to flatter the
demo:

- **Tasks (0.35)** — of the work *in play in a 7-day window around the day* (due in it, or
  completed in it), what share was done by then.
- **Focus (0.15)** — minutes logged that day against the daily target.
- **Habits (0.25)** — trailing 7-day completion rate per habit, averaged.
- **Goals (0.25)** — average progress *as of that day*, over goals with known work.
- **Overdue penalty** — 3 points each, capped at 15, counted as of that day.

And the rule that makes it honest: **a term with nothing to measure is excluded and the
weights renormalise**, never scored as 0 — the same "counting silence as a middle-of-the-road 3
is a fabricated number" rule the Journal established in M33. `nexusScore()` then returns today's
fold, the delta against the previous *day* in the history (not against a stored badge), and the
14-day series the sparkline draws.

## Milestone 35 — Automation (the second Pro feature)

`index.html` 942,458 bytes. One new entity, one new page, one new derived family, **DB v4**.
Verified by `t36.js` — **96/96 checks, port 9555**.

### The governing principle

**An automation is a stored INTENTION.** A rule stores its schedule and its action — *what
should happen* — and never what it produced. What it has produced is the **inverse** of the
`origin` stamp carried by the records themselves, exactly as `filesFor()` is the inverse of a
file's `refs`. A stored output list could disagree with the records; a scan cannot.

**And the engine is a fold, not a scheduler.** There is no background process and no
`setInterval`. A timer would be theatre: it cannot fire while the app is closed, so it could
only ever lie about what happened. Instead, on load the engine asks what each enabled rule
*should* have produced and makes up the difference, then stores a `lastRun` high-water mark so
the catch-up is idempotent. The generalisation: **any "recurring" feature is a fold over
elapsed time, computed when it is asked, and it must be safe to run twice.**

**Provenance is the one link that cannot be derived.** Everything else on a record is computed
at render time, but *where a record came from* is a fact only the writer knows. So
`origin: {rule, day}` is **stored** — the first narrow exception to "derived, never stored".
It is validated by `normalizeOrigin()` (both fields required, `day` must match
`/^\d{4}-\d{2}-\d{2}$/`) and is `null` on every hand-written record, so the key is uniform
rather than ragged.

### Data-model changes

- **`normalizeAutomation(r)`** → `{id, name, enabled, trigger:{every, dow, dom, at}, action,

  `dom` is **clamped 1–28 so every month has that day** (the 31st would silently skip
  February); `at` is validated against `/^([01]\d|2[0-3]):[0-5]\d$/` else falls back to
  `'08:00'`. `lastRunDaysAgo` / `createdDaysAgo` resolve **once** at hydrate, then persist as
  real day keys — the same boundary-parser rule as `dayOffset`.
- **`AUTOMATION_TRIGGERS` / `AUTOMATION_ACTIONS`** drive both the chips and the editor; a new
  action is one entry plus a branch in `_materialise`.
- **`DB_VERSION = 4`**, `'automations'` appended to `STORES`, `automations: 'automations'` in
  `Repo.map`, `out.automations` in `_reconcile` and `Repo.seed`, `get/set automations()` on
  `State`. `ACTIVITY_KINDS` gained `automation` (route `automation`, colour `var(--warn)`).
- **`origin` added to `normalizeTask`, `normalizeNote` and `normalizeInbox`** — the three
  things a rule can make. (Consequence: t23's note-field allowlist had to admit `origin`; it

### The ordering bug (the one worth remembering)

The activity log is stored newest-first by `unshift` but is **re-sorted by `createdAt` on
hydrate**, so if insertion order and timestamp order ever disagree the log silently reorders
itself across a reload. `activateDemoPro()` captured `now`, called `setEntitlement()` — which
emits, and whose subscriber now runs the automation engine, which logs its own entries — and
only *then* unshifted its own entry with the **earlier** timestamp. Measured: the activation
entry sat above the engine's records in memory and below them after a reload.

Found by diffing the **set** rather than the count: the failure read `30 → 30` entries with a
changed head, which ruled out data loss and pointed at order. Fixed by writing the log entry
*before* the side effects in both `activateDemoPro` and `revertToFree`. Rule of thumb — **if a
method both mutates the log and triggers a chain that can log, write the entry first.**

## Milestone 36 — Notifications (the bell)

### The governing principle
**A notification is a statement that is currently true.** The bell has no inbox of
its own. `Derive.notifications()` is a **fold over existing derivations** —
`overdueTasks`, `financeBudgets`, `habitStreak`, `inboxAgeDays`, `journalStreak`,
`automationSummary` — so an alert cannot disagree with the page it is telling you
about, and it disappears the moment its cause does, **with no dismissal needed**.
Nothing is authored, nothing is scheduled, nothing is cached.

The consequence to design *around* is that an alert can only ever be as good as the
derivation underneath it. That is why two obvious candidates were **deliberately
left out**: goal and project deadlines, because `deadline` is free text (`'30 Sep'`)
that was never resolved to a date — an alert built on it would be built on a string.
And "budget close to target" is out too: *close* is a judgement, *over* is a fact.

### Data model
**Nothing derived is stored.** The only stored part of a notification is the user's
own **decision** — `read` / `dismissed` — and it lives in `Settings` (localStorage),
beside every other preference. Small, synchronous, and it needs **no DB bump**.

The alert **key is load-bearing**, and its scoping *is* the design:
- *day-scoped* keys carry the day (`habit:h2:2026-09-14`) — so today's decision
  cannot silence tomorrow's;
- *record-scoped* keys carry only the id (`overdue:t18`) — because the condition is
  the same condition until the record is dealt with.

Six kinds, ranked: `overdue` 3 · `budget` 3 · `habit` 2 · `inbox` 2 · `journal` 1 ·
`automation` 1. Sorted rank DESC → `at` DESC → key ASC, so ties are stable and the
list cannot reshuffle between repaints.

New derivations: `overdueDays(t)` (how late, in whole days), `notifications()`,
`notificationView(filter)`, `firstOfNextMonth(monthKey)`. New `State` methods:
`_notifMap`, `notificationDecision`, `_writeNotification`, `markNotificationRead`,
`dismissNotification`, `restoreNotification`, `markAllNotificationsRead`,
`clearNotificationState`, `pruneNotificationState`. New surface: the `Notifications`
panel module behind the header bell, `Shell.syncNotifications()` (the badge is a
**view** of the derived list, recomputed on the shared state signal — the same rule
`syncPlan()` follows), and the CSS block.

The demo yields **5 alerts**: 1 overdue (`t18`, 3 days late), 1 habit (`h2`, 4-day
streak unlogged), 2 inbox (`i9`/`i10`, waiting 4 and 5 days), 1 journal (3-day
streak). 0 budget (none over), 0 automation (the gate is shut on Free).

### Bugs found and fixed
1. **A real design gap, found by re-reading rather than by a test.** The comment
   claimed `until` kept the decision map bounded — true for day-scoped alerts, but
   `until` is `null` on every **record-scoped** alert (overdue, inbox, automation),
   and a `null` expiry is never pruned. So a decision about a completed task or a
   triaged capture would sit in localStorage for the life of the workspace.
   **Fix:** `pruneNotificationState()` now drops a decision for **two independent
   reasons** — it has *expired* (`until <= today`) **or** it is *no longer about
   anything* (its key is absent from today's derivation). The second rule is the
   real bound: the map is now sized by what is currently true, not by the age of the
   workspace. This is invariant **15** in the skill.
2. **Polish, caught by looking at the screenshot:** the panel foot read
   `Restore 0 dismissed` when nothing was dismissed. Now `Restore dismissed`.
3. **Polish, caught while probing:** the overdue alert's detail was the due date
   (`11 Sep · Racing Game`), which restates what the row already implies. Now
   `${late} day(s) late · ${project}` — lateness is the actionable fact. This is what
   `overdueDays()` was added for.

### Suite bugs (mine, not the app's)
- **`markAllNotificationsRead()` read as `undefined`.** I asserted on `first` before
  ever assigning it — the probe only had `second`, which therefore marked all 5.
  The fix exposed a better assertion pair: *reports how many it marked* (5) and
  *marking again reports nothing left* (0).
- **`SyntaxError: Unexpected token '+'`** — I wrote a computed key as an object
  literal (`{ "stale:" + past: {...} }`), which is not JS. Built the map with
  assignment instead.
- **The `.card-sub` collision — a genuinely reusable trap (now trap 13 in the
  skill).** The empty-state assertion failed with `"4 done · 1 open"`: a **dashboard**
  card. `.card-sub` is a short class reused across surfaces, and a panel is appended
  to `#overlay-root` *on top of* the still-mounted page, so `document.querySelector`
  matched the page behind the overlay. The app was right; the selector was not.
  **Scope every selector for an overlaid surface to the surface.**

## Milestone 37 — Templates (the third and last Pro feature)

### The governing principle

**A template stores a SHAPE, never a date.**

That single sentence is the whole feature, and everything else follows from it. A
template is a **named bundle of records to create** — a project and its starter
tasks, a weekly review, a packing list. Its only time field is an **offset**
(`dueIn`), resolved to a real `YYYY-MM-DD` key at *apply* time and nowhere else.
A stored `due` would freeze one application's answer into the template, so the same
template applied in January and in September would make January work.

### The design decision: a sibling, not a copy

Templates is **Automation's sibling**. Both speak the same action vocabulary
(`AUTOMATION_ACTIONS`) and both resolve `{date}` through the same
`Derive.automationTemplate()`. Writing a second dialect would guarantee drift, so
there is exactly one.

The difference is deliberate and is the point of the feature:

| | Automation | Templates |
|---|---|---|
| Nature | a **rule**, **scheduled** | a **verb**, **invoked** |
| Semantics | a fold over elapsed time | an explicit act |
| Run twice | changes nothing | makes twice as much |

`t38` asserts that contrast directly: applying `tp3` twice walks the task count
33 → 36 → 39, while running the "Morning plan" rule twice makes 1 then 0.

### Data model

- Entity: `{id, name, icon, items[], createdAt, updatedAt}`. An item is
  `{type: 'task'|'capture'|'note', …}` normalised through `normalizeTemplateItem`,
  which reuses `AUTOMATION_ACTIONS` so an unknown kind falls back to a task.
- `TEMPLATE_ICONS` (12) + `TEMPLATE_MAX_ITEMS = 12`. `normalizeTemplate` guarantees
  a template is **never empty** — a template that makes nothing is not a template —
  so `{name:'', items:[]}` normalises to `Untitled template` with one item.
- `dueIn` is clamped 0–30 so a template cannot park work a month out.
- **DB v5** (`templates` store added to `STORES`, `Repo.map`, `Repo.seed`,
  `State._reconcile`). `onupgradeneeded` only creates missing stores, so an existing
  workspace keeps everything.
- A new `ACTIVITY_KINDS` entry (`template`) so applying and deleting are logged.
  t31 derives its expectations from the table, so it absorbed the addition unchanged.

### One resolution point

`Derive.templateItem(item, day, vars)` is the **single** place a shape becomes a
record. `templatePreview()` and `State.applyTemplate()` both go through it, so the
card **cannot promise what Apply does not deliver** — asserted directly by comparing
the previewed bundle against what was actually created.

Two hole tokens, and they are different *kinds* of thing:

- `{date}` **resolves by itself**, so a template that only uses it still applies in
  one click (`templateHoles()` deliberately excludes it).
- `{name}` is **asked for at apply time and never stored**. `applyTemplate()`
  *refuses* when a hole is unanswered rather than guessing, and whitespace is not an
  answer. The answer reaches every field it appears in, including the project.

Deleting a template destroys **nothing else**: the records it made are ordinary
records with no link back, and the confirm dialog says so.

### The one design gap found by re-reading, not by a test

`normalizeTemplate` was fine, but the **`{name}` answer had no home**: the editor
showed a `{name}` placeholder and the card offered Apply, yet nothing collected the
answer before creating. Building `_ask()` (the hole dialog) closed it. Worth noting
because the surface *looked* complete — the gap was only visible by walking the
apply path end to end.

### Suite bugs found (all in `t38`, all mine, none an app bug)

1. **`searchAll().matches.filter is not a function`.** `matches` is a **count map**
   (`{task: 3, note: 1}`), not an array — the array is `groups[].hits[]`. Fixed by
   flattening `groups` and matching on `id`.
2. **A summary assertion that could never pass.** I checked
   `summary.indexOf(String(items.length)) !== -1`, but for a mixed bundle the item
   count never appears verbatim (`items.length === 5` vs `"4 tasks · 1 note"`).
   Replaced with a hand-built expectation (pluralised per kind, canonical order) —
   a real check instead of a substring guess.
3. **A selector whose *text* was invalid JS.** `[data-i="1"]` inside a
   double-quoted JS string terminates the string; the expression then parses as
   `1 "])"` and Chrome reports *missing ) after argument list*. Switched to
   filtering `querySelectorAll` by `getAttribute`.
4. **`[data-i=1]` is not valid CSS** — a numeric attribute value must be quoted.
5. **A carry-across test aimed at the wrong row.** The typing went into row 0 but
   the kind switch was clicked on row 1 (the empty one), so the app looked broken
   when it was correct. Now the second row is typed into first.
6. **A confirm-dialog assertion in the wrong grammatical number** — the copy is
   "Every record it ever made **stays exactly where it is**", the test expected the

### The harness bug — and the real finding of this milestone

The first full sweep **hung on t15 for 900 s** after three passing checks, and t15
then passed **44/44 standalone**. Root cause: `send()` resolves *only* from
`ws.on('message')`, so if the CDP target dies (renderer crash, a browser killed by
the next suite's `kill_port`, OOM under load) the pending promise **never settles**
and the suite hangs with no output. The sweep then reports a silent 900 s stall that
reads exactly like a code regression.

This is the **third** occurrence of this class (M35 t26, M37 t15) and the first time
it was understood. Both ends are now guarded:

- every suite's `send()` carries a **60 s deadline** that rejects with the method
  name, so the same situation fails in a minute with a legible `HARNESS ERROR`
  (19 suites via `armtimeout.js`, plus the 4 external ones that use a `pending` Map);
- `sweep.sh` gained `clear_test_ports()` — **every** test port (9381–9570) cleared in
  one `netstat` pass plus a 2 s settle before each suite, not just the port it is
  about to use.

Also learned: **do not start a sweep immediately after running suites by hand** —
`proc.kill()` kills the Chrome *browser* process, and on Windows its renderers can
outlive it. Recorded as **trap 14** in the skill.

## Milestone 38 — Onboarding, and the first real Settings page

### The governing principle

Onboarding asks only what the app **cannot derive**, and every answer must be *read
by something* or the questions are a survey. Two questions, both consumed:

| Answer | Stored as | Read by |
|---|---|---|
| What to call you | `user.name` | the dashboard greeting **and** the sidebar profile chip |
| Where to start | `user.focus` | a "Your focus" strip on the dashboard |

`user.onboardedAt` is a **number or `null`**, never a boolean. `null` means "never
seen", which is what makes the first run identifiable *and* re-running possible.

### The decisions

- **Nothing is written until the user commits.** The flow holds a `_draft` in memory
  and only `finish()` calls `completeOnboarding()`. Abandoning it at any step leaves
  the workspace byte-identical — asserted, not assumed.
- **Closing is not a decision.** The banner's "Not now" is the only silent one. Skip
  and Finish are the **same write** (`onboardedAt`), so a skip can never leave a
  half-set-up workspace.
- **Finish goes somewhere.** It navigates to the chosen starting point rather than
  showing a "done" screen — the last thing a first run does is take you to work.
- **One table.** `START_HERE` is the only list of starting points; `setUserFocus()`
  filters and orders by it, so the flow's chips, the dashboard strip and the Settings
  chips cannot disagree about what exists or what order it is in.
- **The offer is a banner, not a wizard.** This workspace already holds demo data, so
  nothing must be answered before looking around.

### `settings` is no longer a stub

The route used to fall through to `__stub`. It is now a real page that owns the
profile onboarding creates, and it is deliberately honest: it shows what exists,
offers the one action that changes it, and **names** what is not built (Export /
Import, demo reset) rather than showing a dead toggle.

### Three real bugs, found by POLISH and by nothing else

1. **A one-shot guard that latched.** `SettingsPage`'s rename used the inline-rename
   pattern — `settled = true` → write → repaint — where the repaint detaches the input
   and fires a second blur the flag is meant to swallow. But the repaint target was
   `Dashboard.render()`, which **early-returns on the `settings` route** (invariant 2).
   Nothing re-bound, so the flag stayed `true` for the whole visit: the first rename
   worked and every later one **silently did nothing while the field showed the new

2. **The sidebar profile chip was static markup.** `<b id="profileName">Alex</b>` had

3. **The avatar was a second copy of the name.** `<span class="avatar">A</span>` sat

### What was built

`Workspace` is a new module between `Onboarding` and `SettingsPage`, plus a **"Take it

- **The envelope stores no derivable number.** No count, no summary — the manifest is read
  off `data` itself, so a hand-edited file cannot claim a count its contents do not
  support. The export *screen* shows counts; the *file* does not bake them in. Size is
  derived from the encoded bytes by `base64Bytes()`, never declared beside them.
- **The plan is not in the file.** An entitlement is live state (invariant 10), so a file
  that could grant Pro would make the gate (invariant 13) meaningless. Import preserves
  the current entitlement and says so out loud.
- **An import goes through `_reconcile`** — the same function a reload uses. That is the
  whole safety property: a file cannot introduce a record shape the app would never write
  itself. The corollary found real work: **every collection needs a normalizer**, and
  M39 found the only two that had none — `projects` and `goals`. A nameless project
  renders blank and can never be matched by the tasks that reference it **by name**, not
  by id. Both now have one, applied in `Repo.seed` *and* `_reconcile` like `normalizeUser`.
- **A Blob does not survive `JSON.stringify`** (it becomes `{}`). File bytes travel as
  base64 beside their mime type and are decoded into a real Blob *before* `_reconcile`,
  because `normalizeFile` drops a record with no bytes — otherwise the user's files would
  vanish silently on import.
- **Refuse rather than half-apply.** `importPreview` validates the marker, the format
  (refusing anything newer), every collection's presence *and* type, the profile, the
  finance block and every file's contents. Any failure returns before a single field is
  touched. A **missing** collection is refused rather than falling back to `DEMO`
  (invariant 4 would otherwise quietly fill it).
- **`_ord` is stripped on the way out** — storage bookkeeping that `persistAll` re-stamps
  on every save, and a file has no business carrying it.
- `EXPORT_COLLECTIONS` is the one table of what a workspace holds — the export's
  counterpart to `START_HERE` — so the summary, the file and the import preview cannot
  disagree about what exists.

Also culled three `Settings` keys that had **no reader anywhere** (`reducedMotion`,
`densities`, `onboarded` — the last superseded by `user.onboardedAt`): *a default nothing
reads is a preference the app only pretends to have.* What remains is `theme` and
`focusTarget`, which is exactly what an export carries.

DB **v5 — no bump**: export/import adds no store, and a new preference never bumps it.

### The bug POLISH found (and no suite could)

This is the fourth milestone where **looking at the screenshot** was the thing that found
the defect — and this time it was exactly the failure the POLISH step names: *a number in
two places that disagree.*

The Settings card read:

> **307 records across 15 kinds, plus 6 files (1.8 KB).**

and the import confirmation repeated it twice — *"The file holds 166 records and 6 files"*,
*"This workspace holds 307 records and 6 files"*.

But `workspaceSummary().records` is `rows.reduce(...)` over **`EXPORT_COLLECTIONS` — which
contains `files`**. So the 307 already included those 6 files, and the chips printed
directly underneath the sentence added up to exactly 307 — with **"Files 6" as one of the
fifteen kinds**. The sentence claimed 313 while the list beside it proved 307. And because
`files` is a *subset* of `records`, "plus"/"and" was arithmetically wrong at all three
sites: the card, the confirm modal's `line()` helper, and the activity entry the import
writes into the *new* log.

The root cause is worth stating plainly, because it is a copy bug with a data shape behind
it: **`records` is a total that already contains `files`, so any copy presenting both must
state the containment.** The fix is one word — "including" — at three sites, plus the
structural assertion that makes it impossible to reintroduce.

Two of the three are now guarded by arithmetic rather than by wording: the suite asserts
`chipSum === workspaceSummary().records`, that the sentence quotes *that same* number, and
that the copy contains no "plus". The log line is asserted to count the files *inside* the
records. Proving it first mattered — the checks were written and **run against the unfixed
app**, where they failed with the exact strings (`… 307 records and 6 files`), and only
then was the copy changed.
