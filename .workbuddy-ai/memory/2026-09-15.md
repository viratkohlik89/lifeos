## Milestone 40 — Demo reset

### What was built

The Settings page's last placeholder became the real thing. The **"Not built yet / What this
page will grow into"** card is gone — M39 removed export/import from its list and M40 removed
the last entry, so there is nothing left for it to name — and in its place is **"The demo /
Put the demo back"**: a description of what a reset restores, one `btn-danger` action, and a
line naming what it leaves alone.

The governing principle, recorded as **invariant 21**: *a reset is the seed, run again.*
`State.resetToDemo()` does not re-implement the demo. `init()`'s seed branch was extracted
into `State.seedDemo()` and `State.demoWorkspace()` (`_reconcile({})`, which falls back to
`DEMO` for every collection), and both paths now call them — so **a reset workspace is the one
a fresh install would have produced**. A second seed path would have been a second definition
of "the demo" and the two would have drifted. This is M39's rule ("an import is a restore
through the same door as a load") applied to the seed.

Four things survive, and the card and the confirmation both say so, because none of them is
the demo's to own:

- **the profile** (`user`) — a reset is not a reason to ask who you are again;
- **the plan** (`entitlement`) — an entitlement is live state (invariant 10); a data
  operation cannot revoke it, exactly as an import cannot grant it;
- **the preferences** (`theme`, `focusTarget`) — they live in localStorage and a record reset
  never touches them; and
- **the user's own alert decisions**, passed through `pruneNotificationState()` so a decision
  about a cause that is back is kept (invariant 16) while one about a record that no longer
  exists is dropped now rather than at the next boot.

**Nothing is written to the log.** An entry describing the reset would make the restored
workspace differ from a first run, which is the whole promise. The user is told by the
confirmation they answered and by the toast afterwards.

`resetToDemo()` wipes, builds the demo, applies the four keeps **before** the write (so
storage never briefly holds the demo's profile — a reload in that window would show the wrong
name), then `Repo.seed()` + `markSeeded()` + prune + emit. DB **v5 — no bump**: no new store.

### Reused, not duplicated

The reset confirmation is the import confirmation's shape, because it is the same kind of act:
it names **both** sides, and it offers **Export first** so the replacement is avoidable. And
because the replacement is knowable, `workspaceSummary()` grew an optional argument so the
modal can describe the demo it is about to install through the same rule as the workspace it
is about to destroy. The wording moved into **one shared helper, `recordSummaryLine()`** —
the M39 double-count had survived at *four* separate sites precisely because each wrote its
own sentence.

Also removed: the now-dead `.set-soon` CSS (4 rules), and the two duplicated `line()` closures.

## Milestone 41 — Dashboard customisation

### What was built

The dashboard stopped being a hand-written layout and became **a table plus an
arrangement**. `DASH_CARDS` is the one table of what it can show — key, label, blurb,
column, span, and the DOM `sel` it renders with — and `Widgets.card(key)` is the one place a
key becomes a card. The page no longer decides what a dashboard contains; it draws what an
arrangement resolves to.

The three cards the ledger had been carrying as missing arrived with it: **Journal** (today's
mood / energy / focus, read off the same `journalList()` the Journal page uses), **Inbox**
(what is still waiting, per-kind chips, and the real age of the oldest from `createdAt`), and
**Activity**, which was a bare five-row feed and is now a summary — "6 today · 20 this week" —
over the same five rows, read through `activitySorted()` rather than off the stored array.

The governing principle, recorded as **invariant 22**: *a dashboard is a table, not a
layout.* Four rules fall out of it, each with a test:

- **Every key has a renderer, and every arrangement key has a `sel` in the DOM.** The suite
  renders all eleven and checks each produces a card, so a table entry nobody can see is
  impossible to ship silently.
- **`null` means never arranged; a real emptiness is kept as one.** `{wide:[],side:[]}` is a
  deliberate answer and survives as one — the same distinction `user.onboardedAt` draws
  between never-asked and answered.
- **A card lives in one column.** `pickDashBoard` drops unknown keys, drops repeats, and lets
  the first list to name a key win.
- **A preference that travels must travel everywhere.** The arrangement joined
  `EXPORT_PREFS`, and each entry there now carries its own `value(v)` formatter instead of the
  export screen and the import preview each branching on the key name.

### The design decision worth recording

The arrangement is `{wide:[…], side:[…]}`, **not a flat ordered list**, and that is forced by
the layout rather than chosen. The dashboard is two columns of *different widths* (the wide
one carries the work, the side one is a stack), so a card's column is part of its identity —
a flat list would have to guess, and every guess would move a card the user did not move.

I first wrote it as a flat list with a `span` per card, then measured: an ordered list cannot
express "habits and money share a row *inside the wide column* while focus and upcoming stack
in the narrow one". An even-columns grid was the alternative and would have relaid the whole
dashboard, because `full` in an even grid is 100% where today it is the 68% wide column. So
the column went into the preference and the default renders exactly what the hand-built
version did — which the suite asserts column for column, card for card.

### POLISH found an app-wide defect

Reading `m41-2-arrange-panel.png` showed "Reset to the default" sitting beside "Done" looking
completely normal — but it was **disabled**. Grepping for it: **the stylesheet had no
`:disabled` rule anywhere, in forty milestones.** So every disabled control in the app — the
arrange panel's first/last move buttons, and every confirm button after a submit — looked
exactly like a live one.

That is the "a visible control must always work" rule broken from the other side: the control
*doesn't* work, and nothing says so. Fixed once in the button component
(`opacity:.4; pointer-events:none`), and the suite now asserts it by **computed opacity**, not
by the attribute — because a suite asserting `disabled === true` sees a correct flag and a
lying button.

### Two more honesty fixes in the same area

1. **The "Daily reminder" was the same sentence every day, forever.** A static copy wearing a
   promise. It is now chosen by the calendar day — deterministic, so it holds still while you
   look at it and has moved on tomorrow. **A random pick would have been the wrong fix**: a
   fabricated rotation that changes on every repaint is worse than never changing.
2. **The empty dashboard said "every card is hidden" beside four visible tiles.** The headline
   stat tiles are page chrome, not part of the arrangement, so the copy now names what is not
   hidden. Denying four things the user can see is a small lie, and the suite asserts the tiles
   are still there.

## Milestone 42 — Notes attachments

### What was built

The last half-built connection in the app is closed. `FILE_REF_TYPES` has listed four
kinds a file can point at since M28 — **task · project · note · journal** — and
`filesFor(type, id)` has always resolved the inverse. The Files page could attach to any
of them. But only the **task** panel ever *showed* the files it had: a note could carry
attachments for forty milestones and never mention them. The connection existed and was
invisible from one side.

The governing principle, recorded as **invariant 23**: *a pointer has two ends, and both
must be visible.* When a table declares a set of things that can be pointed at, every
member needs a surface that reads the inverse — otherwise the app is quietly
half-connected, and the half that is missing is the one the user is looking at. It is
invariant 15's "a cascade must reach every surface" applied to pointers rather than to
mutations.

So the note editor's relations block gained an **Attached** row — placed after Related
and before Contains — carrying the same `.fb-list` rows the task panel uses, the same
"Attach a file" affordance, and an honest empty line. Attaching goes through
`FilesPage.attachTo('note', …)`, the same call the Files page makes, so there is one way
to attach rather than two. And the **note card gained a paperclip count** in its foot,
symmetric with the existing folder and layers counts, so the list shows it too.

### Three things found while finishing it

1. **Following a pointer had two implementations.** The task panel hand-rolled
   `Overlay.close(); Router.go('files'); setTimeout(openPreview, 130)`, while
   `revealRecord(type, id)` already existed as the one table saying where a record of
   each kind lives — and it knows the route might *already* be open. Both call sites now
   go through it.
2. **The note editor uses no element ids at all** — everything is a `data-ne-*`
   attribute, because the editor can be mounted twice (the desktop pane and the mobile
   panel) and two elements with one id is invalid. I first wrote `id="ne-filein"`, then
   grepped and found zero `id="ne-*"` in the file, so it became `data-ne-filein` and the
   binding is scoped to the relations block (which also satisfies trap 13).
3. **A dangling pointer is kept and reported, not silently pruned** — and M42 checked
   rather than assumed. The policy was already documented for notes and inbox captures,
   and it holds here: deleting a note leaves the file's pointer and the Files preview
   says "This record no longer exists", with no dead link offered. **No lifecycle change
   was needed**, which is worth recording because the opposite was the obvious
   assumption.

## Disk audit + harness fix — `C:/tmp` (not a milestone)

The user reported ~20 GB in `C:/tmp`. Measured: **20,218 MB (19.74 GB)**, 432 directories.

**What it was.** 431 were Chrome `--user-data-dir` profiles from CDP test runs; the 432nd was
`snakebuild` — five "Neon Snake 3D" fragments dated 1 Sep, from a **different project** (a
superseded iteration of `Desktop\Snake_game`, which is not a git repo, so it is the only copy
of that version).

**Root cause, and it is a real harness defect.** Every suite passes `--user-data-dir=/tmp/nx…`.
On Windows a leading `/tmp/…` is a **drive-relative** path, so Chrome resolved it against the
current drive and created `C:/tmp/nx…`. `C:/tmp` is not `%TEMP%`, so no cleanup tool owned it.
It stayed invisible because **t25–t35 used an absolute path and were correct** — half the
suites were clean, which hid the half that were not.

**Fix, in two parts:**
1. All 50 files in `nexustest/` now use `C:/Users/punit/AppData/Local/Temp/…`; the skill's
   `cdp-harness.js` template carries the same path **with the reason in a comment**, so no
   future suite repeats it.
2. Every suite that launches Chrome (**t8 · t15 · t17 · t19 · t20 · t36–t43**) now removes its
   own profile on exit, sweeping by its own prefix so a crashed run is collected too.

**Verified, not assumed:** `C:/tmp` had 432 entries before a t43 run and 432 after; the profile
appeared in `%TEMP%`; the second run then removed the leftover (1 → 0); t41 and t43 still pass
45/45 and 38/38.

**Also found:** `%TEMP%` had accumulated **379 profiles / 9.20 GB** of its own — same cause, one
directory over. Self-cleanup fixes that too. Recorded as trap 21.

## Milestone 43 — the dead-hook gate

### Why this one exists

Every previous milestone was verified by clicking things in a browser. That can only
ever prove that **the controls a suite already knows about** work. It cannot see a
control that was never wired up — and "every visible control works" is the rule the
whole app is built on. So M43 is the first **static** gate: it reads the source and
asks what nothing is listening to.

`scripts/check_dead_hooks.py` (installed into the skill, wired into the loop as
**Step 2b**) checks two things:

1. **A `data-*` hook written into the markup that nothing reads** — not the app, not
   any suite. Such an attribute is a hook wired to nothing: it looks like an
   affordance and leads nowhere. The suites are scanned as *readers* (96 files), so a
   legitimate test handle is never reported — t19 addresses goals with
   `.goal-card[data-gl="…"]`, and that is a live hook, not a dead one. My first cut
   scanned only the app and reported 19 false positives for exactly this reason; the
   honest version reports 5.
2. **A `<button>` with neither an `id` nor a `data-*` attribute** — unreachable by
   every binding style the app uses, so almost certainly a button that does nothing.
   Reported for review rather than deleted blindly, because a class-based binding
   would be invisible to the check.

### What it found

**5 dead hooks**, all of the same shape: an identity attribute on a **card wrapper**
whose real controls were children with their own hooks, left behind by earlier
milestones and read by nothing.

| hook | where | why it was dead |
|---|---|---|
| `data-shell-mounted` | `#nexus-root` | a mount marker nothing consulted |
| `data-kn-node` | knowledge node | the row's own controls carry the hooks |
| `data-sc-group` | score group cards | ditto |
| `data-au` | automation rule cards | children use `data-au-toggle/run/edit/…` |
| `data-tp` | template cards | children use `data-tp-edit/apply/del/…` |

Each was verified dead three ways before removal: absent from the app's read forms,
absent from all 96 suite files, and **not styled as clickable** (no `cursor:pointer`,
no `role="button"`) — so they were inert markup rather than broken controls. Removed.
A card-level handle added in future must arrive **with** its reader, or it is dead the
moment it is written.

**0 unhooked buttons** — 394 `<button>` tags and every one carries an `id` or a
`data-*` hook. That is a genuinely verified property of the app now, not a hope.

## Milestone 44 — Motion: the premium pass

### What was built

The app already had a motion *foundation* — four timing tokens, eight keyframes, 96
transitions, and a `prefers-reduced-motion` block. M44 turned it into a **system** and
filled the gaps: six durations and three curves, all in `:root`, and nothing anywhere
else inventing its own.

| what | how |
|---|---|
| **route change** | `pageIn` — a 190ms rise with a hair of scale |
| **card entrance** | `Motion.enter()` runs once per route: cards in view get `data-mot="in"` and a `--i` for a 34ms stagger; cards below the fold are held at `data-mot="hold"` until an `IntersectionObserver` reveals them |
| **repaints** | deliberately NOT animated — an instant update is what makes editing feel responsive |
| **hover** | cards catch more light (border + deeper shadow); only cards that ARE a target lift, because there the lift is the affordance |
| **press** | `scale(.97)` on buttons, `.88` on checkboxes — the one moment a control should feel like an object |
| **theme change** | `html.theme-anim` for exactly 260ms, colour properties only |
| **the nav** | one `.nav-pill` element that *travels*, positioned from the active item's own `offsetTop`/`offsetHeight` |
| **rings** | `ringIn` animates `stroke-dashoffset` from `--ring-c` to `--ring-off` |
| **scroll** | `Motion.scroll()` in a rAF: a progress rail and an `is-scrolled` body class for header depth |
| **glass** | `blur(22-28px) saturate(180-190%)` — `saturate()` is what separates real glass from a grey blur |
| **depth** | every shadow token is now **layered** — a tight contact shadow plus a wide ambient one |

### The two rules that decided what may move

- **Never animate a number a surface displays.** Checked first, and it changed the
  plan: **sixteen suites read `.stat-tile .t-display`**, so the count-up animation that
  a "premium pass" would normally reach for is off the table. A number that is still
  travelling is a number that is briefly wrong, to a test and to a person.
- **Animate `transform` and `opacity` only.** Neither can reflow a page, so nothing
  added here can change a measurement any suite takes.

Both were verified against the suites *before* writing the CSS — no suite scrolls, none
reads `stroke-dashoffset`, and the six that change themes non-silently all `sleep(1200+)`
"to let the theme cross-fade settle". That last one is why the crossfade is safe.

### A real bug found by looking

**The light theme never overrode `--sh-sm`.** It overrode `--sh-md/lg/xl/inset`, so every
light-theme card was wearing the *dark* theme's `rgba(0,0,0,.32)` contact shadow — a
harsh black line under a white card. **A token a theme does not override is a token that
theme inherits by accident.** Fixed with a full layered, blue-tinted light set.

### And one in my own CSS, which is the better lesson

`animation: motIn var(--t-slow) var(--e-out) both` — **invalid**. The duration tokens are
self-contained (each already carries its curve), so that is two timing functions in one
shorthand, and the browser drops the **entire declaration** without a word. The entrance
animation never ran. Nothing looked wrong: a card with no entrance animation is just a
card — visible, positioned, and passing every assertion about its text and geometry.

My first probe checked `opacity` and `transform` and reported a clean pass. It only fell
out when the probe was changed to assert `getComputedStyle(x).animationName === 'motIn'`.
**Checking that a thing is visible is not checking that it animates** — now an editing-
discipline rule in the skill, because the same shape applies to any invalid value.

### Two exceptions that are easy to get wrong

- **The focus ring must NOT animate.** `#focusRing .ring-val{animation:none}` — the timer
  is *driven*: `syncRing()` writes its `stroke-dashoffset` every second, and a CSS
  animation **wins over the attribute**, so the ring would freeze on screen while the
  clock ran on underneath. A decorative ring animates; a live gauge does not.
- **The crossfade is scoped, not permanent.** A standing transition on `color` would make
  every computed style in the app a moving target. Scoped to 260ms around the change, the
  app is only ever mid-flight while the user is watching it.

`prefers-reduced-motion` kills the lot in one block **and forces `[data-mot="hold"]`
visible** — an element held back for an entrance that will never run must not stay
invisible. Verified by emulating the media feature: 15 cards, **0 invisible**, 0 markers.

### Verified

Probe: entrance animation `motIn` with a real stagger; the nav pill at `translateY(36px)`
matching the active item's `offsetTop` of 36; the scroll rail tracking; `ringIn@static`
and `none@focus`; a tab switch animating in with nothing left hidden; and reduced motion
leaving everything visible. Zero console errors.

`index.html` → **1,116,567 bytes**. DB **v5** (no bump — presentation only).

## Milestone 45 — Pricing & upgrade

### What was asked, and why it was a real gap

A screenshot of the sidebar's **Personal** workspace switcher: clicking it toasted
"Multiple workspaces are a NEXUS Pro feature", and the user asked the obvious thing —
*how does someone actually take Pro?* Fine to be in development, but a real user needs a
page that opens with prices where they can buy it.

They were right, and it was worse than it looked. M33 built a Pro page, so the *feature*
existed — but it answered "what does Pro add?" and never "what does it cost, and how do I
get it?". There was no price anywhere in the app. The switcher's sentence **named a thing
that could not be bought**, which is the dead-control rule (invariant 5) broken in prose.

### The shape it took

**A pricing page, not a paywall.** One hero, a monthly/yearly toggle, three cards
(Free · Pro monthly $5 · Pro yearly $40), a 12-row comparison table, a licence panel that
only appears once you own one, five questions, and the honest notice. The free tier is
*sixteen core modules with no record limit* — Pro adds four features that work across the
workspace, and the copy says that rather than implying the app is crippled.

**Three rules, and the first is the interesting one.**

1. **A price is data; every number beside it is derived.** `PLANS` writes `5` and `40`
   down once. The saving (`planSaving()`), the monthly equivalent (`planPerMonth()` — the
   yearly price ÷ 365 × 30.44, so "$3.34 a month" is *computed*, not claimed), the renewal
   date (`periodStart + plan.days`), the days left, and the whole comparison table are all
   read out of those two numbers. **A hardcoded "save 33%" is a claim that drifts the
   moment the prices move, and nothing fails when it does.** The suite asserts the
   *rendered string equals the derived number* — that is the only check that catches a
   page formatting a stored string.

2. **Nothing is sold that does not exist.** The comparison matrix carries a `planned: true`
   row — cloud sync — that renders "Planned" on **both** columns. It is local-first with no
   server, so cloud sync cannot be a checkmark. It carries no gate key either: you cannot
   be denied a feature that was never built.

3. **A tier is a period, not a second entitlement.** `State.billing` is
   `'monthly' | 'yearly' | 'free'`; `entitlement.plan` stays `'PRO'` and
   `FeatureAccess.allows()` still ignores its key, because there is still exactly one thing
   to be. Three prices are three ways to pay for the same one.

### The licence model

Unchanged from M33 and deliberately so: **a local licence with no payment, no account and
no server** — chosen after asking, and the honest option was the recommended one. `PLANS`
supplies the two new fields (`billing`, `periodStart`); everything else is as it was.

- `State.activatePro(billing)` — validates the key against `PLANS` rather than trusting it,
  because the caller is a button in the DOM and **a button is not an API**. An unknown key
  would leave a licence with no price and no period, and the page would then have to invent
  both. Logs first, then changes the plan (the M33 ordering rule — the log must read the
  same before and after a reload).
- `State.switchBilling(to)` — **keeps the licence** (same id, same `startDate`, same
  device) and only resets `periodStart`. A switch is a new period, not a new licence.
- `State.revertToFree()` — clears the licence and nothing else.

`normalizeEntitlement` runs on every load: the two new fields do not exist on an M33
licence, and a Pro licence with no period must not be left for the page to guess at. A Pro
licence with no `periodStart` is dated from its own `startDate` and reads as monthly.

### The upgrade flow

Choose plan on a card → **a confirmation that states the price back** (plan, billing,
price, access, and the no-payment line on the same screen as the button) → the licence
flips → a toast → the page re-renders. Switching periods and cancelling both confirm
first; cancelling says what is lost **and what is not** (every record stays — verified:
22 tasks and 5 notes survive a round trip). Choosing the Free card routes through the
cancel path, because a downgrade is not a purchase.

`ProPage.pick` (which card is highlighted) is kept **separate** from `State.billing` (what
was bought) — that separation is why the page can offer a plan without pretending it was
already taken.

### The entry points

- **The workspace switcher** — a real panel now: what a workspace is, the live workspace
  with real counts (read off the *same* `Derive.workspaceSummary()` the export screen uses,
  so the panel cannot claim a different total), a locked "Add a workspace" slot, and one
  "See pricing" button while Free.
- **The header** — a new Upgrade button, shown by `Shell.syncPlan()` from the same fact
  that colours the sidebar chips, so the two cannot disagree.
- **The locked page** (`renderLocked`) and the palette already pointed at `pro`; they now
  point at something real.
- **The sidebar chips** — `wsPlan` now reads "Pro · per year" rather than "Pro plan",
  because the period is a fact worth showing and it is already to hand.

### The bug that passed all three gates

The header button was written as **static markup** with `${icon('sparkles', 13)}` in it.
It rendered the literal text. Nothing failed: `${…}` is not an HTML syntax error,
`check_js.py` never sees it (outside `<script>`), the brace balance still matched, and
`check_dead_hooks.py` saw a button with an id and was satisfied. The screenshot caught it
in one look. `icon()` is a JS helper and cannot run in static HTML — the fix is an inline
`<svg>`, like every other static control in the shell. Recorded as **trap 22**, with a
one-line scan of the `<body>`-to-`<script>` region to catch it before a browser does.

### Three suites broke, and two of them were the suites' own fault

The sweep came back with four red suites. Working out which side was wrong mattered:

- **t34/t36/t38/t41 — the suite's fault.** Renaming `activateDemoPro` →
  `activatePro(billing)` broke every caller, because **`State` is a public surface with
  thirty test files reaching into it through `window.__NEXUS__`**. The rename was cosmetic,
  so a thin alias was the right answer — not a second implementation. **Trap 23.**
- **t34 again — the app was right.** It asserted the sidebar chip equalled the literal
  `'Pro plan'`; M45 made the chip say `Pro · per month`, because the period is worth
  showing and the entitlement already carries it. **A test that fails when the copy
  improves is a test that gets "fixed" by making the app worse. Assert the shape, not the
  words. Trap 24.**
- **t37 — the harness's fault, and the subtle one.** It read the notification panel's
  colours 500 ms after applying the light theme and got **midnight** values while the
  attribute already said `light`. Measured by hand: still dark at 500 ms, correct at
  1400 ms. Cause: M44's 260 ms crossfade does not reliably advance while
  `Emulation.clearDeviceMetricsOverride` is re-laying-out the page. **The app was correct
  and I nearly "fixed" it.** The assertion now polls the property instead of sleeping.
  **Trap 25.**

### The bug that no gate could catch

The header's upgrade button was written in **static markup** with `${icon('sparkles',13)}`
inside it, and rendered that call as literal text. `check_js.py` never sees it (outside
`<script>`), the brace balance still matched, and `check_dead_hooks.py` was satisfied by
the id. Only the screenshot caught it. **Trap 22**, with a one-line scan of the
`<body>`→`<script>` region to catch it before a browser does.

### Verified

New suite **`t45` (71 checks, port 9600)** — the first suite whose subject is money. It
proves the derived numbers equal the displayed ones, walks the full flow (choose → confirm
→ licence → gate → reload), pins that a period switch keeps the licence, checks the M33
licence is repaired on load, and confirms cancelling destroys nothing.

The headline suite counts for this milestone: `t45 71 · t34 94 · t37 85 · t41 45`.
Full sweep: **30 suites, 2,588 checks, all green.** Screenshots: `m45-a-pricing` ·
`m45-b-confirm` · `m45-c-pro` · `m45-d-mobile` · `m45-e-light` · `m45-f-workspace-panel` ·
`m45-g-from-switcher`.

The M33 `.pro-grid`/`.pro-feat*` CSS was deleted — the page that used it no longer exists,
and the project's rule is that every rule must have a consumer (the same rule the dead-hook

`sweep.sh` gained t44 (motion, 9595) and t45 (9600); its stale-port regex was widened to
`96xx`. `index.html` → **1,182,062 bytes**. DB **v5** (no bump — one field pair on a
