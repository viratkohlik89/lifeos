## 2026-09-13 — Milestone 17: Projects page (derived, not decorated)

**Deliverable:** `index.html` now **243,425 bytes**, still one file / no build / offline.

### Governing principle applied here
Project progress is **derived, never stored**. There is no `project.progress` field
in state anymore — every number on the page is computed from `State.tasks` filtered
by project name at render time. This is what makes the cascade real: complete a task
anywhere and the project card, the project list rollup, the palette result, the
dashboard tile and the NEXUS Score all move together, because they all read the
same derivation.

### Added
- **`Derive.projectStats(name)`** → `{total, done, open, overdue, high, progress,
  openMinutes, linked, health}`. `progress = round(done / total * 100)` over
  non-archived tasks; `health` is a deterministic threshold read
  (overdue>0 → *At risk*; ≥80% → *On track*; ≥40% → *On track*;
  else *Getting started*).
- **`Derive.allProjects()`** → merges **declared** project records with project
  names *only used by tasks* (so a task typed into a new project name surfaces that
  project), derives `status` (*Complete* when nothing is open), assigns a
  **deterministic auto colour** via a stable string hash, and sorts
  Active → other → Complete, then by open work, then name.
- **`Derive.projectList()`** → page-level rollup `{list, active, openTasks,
  doneTasks, atRisk, avg}` for the summary strip.
- **`ProjectsPage`** — summary strip, filter tabs (`all | active | risk | complete`)
  with live counts, responsive card grid, per-card progress bar + ring, open/done
  counts, overdue/high attention flags, deadline, an "open work" empty state, and a
  "New project" modal.
- **`ProjectDetail`** side panel — rename, status, deadline, task list with inline
  toggle, "add task to this project", **Delete project** with confirmation.
- New `State` mutations: `addProject`, `updateProject`, `deleteProject`.

### Demo data corrected
- `DEMO.projects` **had fake `progress` and `tasks` numbers**. Stripped both — records
  now carry only `id/name/status/deadline/color`.
- Grew `DEMO.tasks` from **9 → 19** so all four declared projects have real work
  (a project showing 0% because it has no tasks teaches the user nothing).
- Command palette project results and the dashboard Project tile now read derived
  stats — the tile says **"1 need attention"** instead of a fabricated "All on track".

### Bugs found and fixed
1. **Project deletion silently failed.** `State.projects` is a *getter with no setter*,
   so `this.projects = this.projects.filter(...)` was a **silent no-op in non-strict
   mode** — the record survived as a phantom while its tasks were reassigned to

2. Removed a fragile `this.projects.pop()` in `updateProject()` that assumed
   `addProject` had pushed last.
3. `deleteProject` now reports how many tasks were reassigned, in the activity feed.

## 2026-09-13 — Milestone 19: Calendar (real events + task due dates)

**Deliverable:** `index.html` now **~316 KB**, still one file / no build / offline.

### The key data-model change
`State.upcoming` events previously had **no date at all** — only a `time`
string. They were effectively "today, forever". Events now carry a real ISO
`date` (`YYYY-MM-DD`), and the demo rows carry a **`dayOffset` anchor** that is
resolved against today exactly **once** (in `normalizeEvent`, during
`_reconcile`) and then persisted as a real date. This means the demo always
looks current without shipping frozen dates, and a *user-created* event is
never silently re-anchored on reload.

### Date helpers (top-level, exported)
`dayKey(d)` → local-time `YYYY-MM-DD` (string-safe for compare + sort, immune to
timezone drift); `shiftDays(d, n)`; `todayKey()`; `normalizeEvent(u)`.

### Added
- **`Derive._dueKey(token)`** — resolves the app's *relative* due tokens onto
  real days: `Today/Tonight/6 PM` → today, `Tomorrow` → +1, `This week` → +5,
  and an explicit `"12 Sep"` token is parsed as the **nearest future** instance
  (rolls to next year if already past).
- **`Derive.dayItems(key)`** → `{events, tasks, all}` for one day.
- **`Derive.monthMatrix(year, month)`** → a **6×7 matrix starting Monday**,
  always 42 cells so the grid never changes height between months. Each cell
  carries `inMonth / isToday / isWeekend / events / tasks / count`.
- **`Derive.calendarSummary(y, m)`** → header rollup (events, tasks due, busy
  days, today count, next busy day).
- **`CalendarPage`** — month grid with a sticky day panel. Clicking a day
  selects it (and switches month if it belongs to another); grid items open the
  real `TaskDetail` / event modals; **layer toggles** for events vs tasks;
  prev/next/Today; "+N more" overflow per cell; a real empty state per day.
- **`CalendarPage.openEvent(id, dateKey)`** — create / edit / delete an event
  with date, time, kind, colour and notes. After saving, the calendar **jumps to
  the event's month and selects its day** so the change is never invisible.
- New `State` mutations: `addEvent`, `updateEvent`, `deleteEvent`.
- Demo `upcoming` grown 4 → 10 events spread across **7 distinct days** including

## M20 ✅ — Habits page (derived streaks from real history)

### What changed
Replaced the cosmetic habit shape (`streak` / `done` / `doneToday` / `target`
counters that only ever incremented) with a real **`history` array of ISO day
keys**. A habit is now just `{ id, name, icon, color, history[] }` — everything
else is computed at render time.

- `normalizeHabit()` — migrates the legacy shape once, resolving numeric
  `dayOffset`-style anchors onto real dates; dedupes, validates the ISO pattern,
  sorts, and caps at 400 entries.
- `Derive.habitStreak()` — walks backwards from today (or yesterday if today
  isn't logged, so a run stays "live" until you actually miss a day).
- `Derive.habitBest()` — longest consecutive run, found by gap detection over
  sorted keys.
- `Derive.habitRate(h, days)` — logged days inside a window.
- `Derive.habitView(h)` — the single source of truth for one habit:
  `doneToday · streak · best · rate7 · rate30 · total · strip[14] · health`.
  Health is a pure function of `rate7`: `Strong ≥6`, `Steady ≥4`, `Slipping ≥2`,
  else `At risk` (and `Unstarted` when there is no history at all).
- `Derive.habitSummary()` — collection-level rollup (`done`, `progress`,
  `bestStreak`, `bestEver`, `weekRate`, and the per-habit views).
- `Derive.currentStreak()` — now reads the real longest live streak, so the
  dashboard "Day Streak" tile stopped being a demo number.
- `State.toggleHabit(id)` / `toggleHabitDay(id, key)` / `addHabit` /
  `updateHabit` / `deleteHabit`. **`toggleHabitDay` refuses future days**
  (`key > todayKey()` → `null`), so history can only ever describe the past.
- `Widgets.habitTracker(ns)` — takes the summary, shows derived done/total,
  real streak per row, `Open` routes to `#habits`, empty state when there are

### Test-harness lessons (for the next milestone)
- **`wrap()` returns a JSON *string*.** Any scalar read back through it must be
  unquoted before being interpolated into the next payload, otherwise you
  generate `x.id===""h1"""` and get a `SyntaxError` from the page, not from node.
  `ev` now prints the offending expression on failure.
- Avoid nested backticks / `${}` inside injected test strings entirely — build
  payloads with plain `'...' + '...'`. `node --check` will not catch a template
  literal whose *interpolation* is malformed at runtime.
- Repaint is explicit in this app: after a direct `State.*` mutation the test
  must call the page's `render()` (or click the real control) before asserting
  on the DOM. Prefer clicking the real control — it tests more.

self-ratings are the only things only the user can supply, so they are the only
things persisted. The streak, the best-ever run, the averages, the month coverage,
the 30-day strip, the tag counts and the search ranking are all derived on every
call — an edit cannot leave a stale number behind, and there is no counter to keep
in sync.

A second principle fell out of the first: **an entry that says nothing is not an
entry.** `journalMeaningful()` requires words or at least one rating, and it gates
the streak, the averages, the timeline and the month grid. A record created by
clicking a rating and then clearing it is invisible everywhere and counts for
nothing — no phantom days inflating a streak.

### Bugs found and fixed
1. **`render()` could resurrect a deleted entry.** The composer's textarea is
   committed before any repaint that would destroy it (`_flushBody`). If the entry
   that textarea was bound to had just been deleted — which is exactly what the
   drawer's delete path does — the flush found no record, fell through to the
   "create on first keystroke" branch, and **re-created the entry the user had just
   removed** from stale text. Fixed by making an explicit `data-jr-body` id
   authoritative: if that record is gone, drop the binding and return null. A stale
   editor is not an authoring intent. (Found by reading the code before testing,
   not by a failing check.)
2. **Double-binding on partial repaints.** `renderList()` rebuilds `#jr-list`, but
   the search box only repaints `#jr-rows` — leaving the aside and the month cells
   live in the DOM. Re-binding the whole container then attached a *second*
   listener to every control that had not been replaced. Fixed with a
   `data-jr-bound` guard on each node before attaching. Without it the tag buttons
   and month cells would fire twice.

### Design flaws found in the POLISH pass (by looking at screenshots)
3. **The month grid sat below the fold.** In Month view the 430 px composer pushed
   the grid down so far that switching tabs appeared to do nothing — the month card
   began at y≈736 on a 1000 px viewport. Fixed by giving Today two sizes: the full
   composer in Timeline (the writing flow) and a **one-line strip** in Month (a
   review lens) that reports today's state and carries a Write button back. Grid
   top moved 736 → 540, so the whole month now fits above the fold.
4. **Month cells were oversized.** `aspect-ratio:1/1` gave ~86 px squares and a
   430 px-tall grid. Replaced with `grid-auto-rows:minmax(50px,auto)`, which reads
   far closer to NEXUS's information density. The composer textarea also came down
   190 → 150 px.

# Milestone 25 — Inbox ✅

  states exactly what will happen rather than over-promising.

  `convertInboxItem` / `reopenInboxItem` / `clearProcessedInbox`, plus the `inbox`
  getter + setter and the `Repo.seed` / `_reconcile` wiring (the `inbox` object

### The governing principle
**A conversion creates a real record through the same code path everything else
uses.** `convertInboxItem` calls `addTask` / `addNote` / `addProject` / `addGoal`
rather than pushing records itself, so a converted capture is an ordinary
workspace object — visible on its own page, counted by its project, included in
the NEXUS Score. The suite proves it the only way that counts: it converts a
capture to a task through the real dialog and then finds that task **on the Tasks
page**. A parallel write path would have produced records only the Inbox could
see.

The second principle: **undo is not a delete.** Un-triaging a capture returns it
to the queue and leaves the task it became untouched; `clearProcessedInbox`
removes only the capture rows. Both are asserted, because "clean up my inbox"
must never mean "silently delete the work".

   the capture box creates on first send rather than on first keystroke.
2. **"Processed" without a destination is an unrenderable state.** `status` and
   `convertedTo` can drift apart (an import, a hand-edited database), and a capture
   marked processed with nothing to point at would vanish from the queue with no
   record of where it went. `normalizeInbox` now demotes any "processed" record
   without a destination back to `'inbox'` — the pointer is the authority.
3. **A raw `href` from a capture is an injection point.** A capture holds whatever
   the user pasted, so `javascript:` would have executed on click. Links now pass
   through a scheme allow-list (`_safeUrl`) and are only rendered when they are
   real `http(s)` URLs.

# Milestone 26 — Finance ✅

`index.html` 565 KB → **634 KB**. New route `#finance` (was a `__stub`).

### What was built
- **`normalizeTransaction` + `normalizeFinance`** — a transaction is `{label,
  amount, type, category, day, note, createdAt}`. The amount is stored as a
  **positive magnitude** and `type` carries the sign, so a "−500 expense" and a
  "500 refund" can never be confused. `day` is a real day key; demo `dayOffset`
  anchors resolve once at hydrate. A category must belong to its side of the
  ledger, so `normalizeTransaction` re-files an impossible pair rather than keeping
  it.
- **`CURRENCIES`** (INR/USD/EUR/GBP) and **`FINANCE_CATEGORIES`** (11 categories,
  each with a colour, an icon and a type). One list drives the form's select, the
  filter chips, the row icons and the breakdown colours.
- **Transactions became a real collection.** `Repo.map` now maps
  `transactions → 'finance'` — a store created unused back in M13, so **no database
  version bump**. `_reconcile` migrates a legacy embedded list once.
- **`buildDemoTransactions()`** — five months of deterministic history from the same
  seeded mulberry32 as `buildDemoFocus`: salary, rent and the recurring bills every
  month, then a realistic spread of discretionary spending, with the current month
  truncated to days that have actually happened.
- **Derive** — `money`, `transactionsSorted`, `financeTotals`, `financeByCategory`,
  `financeMonth`, `financeTrend`, `financeRange`, `financeSummary`, `financeSearch`,
  `financeList`, plus shared `longDay`/`shortDay` (Journal's private formatters now
  delegate, so the wording lives in one place).
- **`FinancePage`** — Month (month navigation, an In/Out/Net/Avg-per-day strip, a
  category breakdown with derived percentages, and the month's transactions grouped
  by day), Trend (six-month income-vs-spending bars, a per-month table, a 30-day
  daily-spend strip) and All (search, type and category filters, paging). The
  add/edit form is a modal with a type toggle that re-offers categories, and the
  currency is a preference in the aside that reformats every figure.

### The governing principle
**The log is the truth.** This milestone was as much a correction as a feature. The
finance singleton used to carry `categories[].value`, `categories[].pct`, a frozen
`weekly` spending array and a `spendPercent` — derived numbers kept in storage. None
of them could be recomputed, and none of them moved when a transaction changed: the
dashboard's seven bars were pure decoration. They are all gone. The singleton now
holds **preferences only** (`currency`), and every figure — month totals, category
percentages, savings rate, the trend, the strip, the dashboard bars — is derived
from the log on every render. The suite asserts the singleton's key list is exactly
`["currency"]`, after a reload too.

### Bugs found and fixed
1. **`data-close` was never wired centrally — so Cancel and ✕ were dead buttons in
   three milestones.** `Overlay.open` only bound a backdrop handler; every modal
   bound its own `[data-close]` delegate, and the modals I wrote in M24 (Journal's
   delete), M25 (Inbox's convert/edit) and M26 (the transaction form) never did.
   Clicking Cancel did nothing. t27 caught it by clicking Cancel, which no earlier
   suite had done. Fixed once, in `Overlay.open` **and** `Overlay.panel`: `data-close`
   is now handled by the component that owns the contract, so a future modal gets
   the behaviour for free. A regression lock was added that clicks both the ✕ and
   the Cancel.
2. **`Math.abs` in a validating path silently flipped the sign of bad input.**
   `addTransaction` computed `Math.abs(Number(amount))`, so passing `-50` did not
   fail — it created a **+50 expense**. Worse, `updateTransaction` turned a patch of
   `{amount: -999}` into `+999`. The sign lives in `type`; a caller's negative amount
   is a bug, not a refund. Both now refuse a non-positive amount, while
   `normalizeTransaction` keeps `Math.abs` because its job is repairing stored data.
   The distinction is the point: **validate at the API, coerce at the boundary.**

# Milestone 27 — Finance part 2: budgets + insights ✅

`index.html` 634 KB → **653 KB**. Two new Finance views; no new route.

### What was built
- **`finance.budgets`** — a monthly target per expense category, living on the
  finance singleton beside `currency`. `normalizeFinance` validates it: a positive
  number against a real EXPENSE category, or the key is dropped. An income category
  can never carry a budget.
- **`State.setBudget(category, amount)`** — refuses an unknown or income category;
  a zero or blank **deletes** the key rather than storing a meaningless `0`.
- **`Derive.financeBudgets(year, month)`** — per-category `target · spent ·
  remaining · pct · over`, plus `all` (every expense category, so the sheet is
  complete), `rows` (the target-or-spend subset), and the rollups `set · unset ·
  totalTarget · totalSpent · totalRemaining · pct · overCount · overBy ·
  unbudgeted`. Ordered so the categories needing attention lead: over budget first,
  then closest to the line, then unbudgeted spending.
- **`Derive.financeInsights(year, month)`** — plain statements read off the log: the
  largest category, spending against last month, savings rate against last month,
  the heaviest day of the week across the whole log, the average day, the largest
  single expense, and the budget position. Each is a `{tone, icon, text}` and none
  hedges or estimates.
- **Two new views** — Budgets (a complete expense sheet with progress bars, per-row
  targets and an over-budget state) and Insights — plus a **budget card in the
  aside**, visible from every view so the budget is never a page you have to
  remember to visit.

### The governing principle
**A value is legitimate to store when it is an INTENTION, not a measurement.**
M26 deleted a stored category breakdown, a frozen weekly array and a `spendPercent`
because all three were derivable. `budgets` survives that cull because there is no
way to derive what you *meant* to spend — a target is a decision the user made. The
test to apply: could a correct derivation produce this from other records? If yes,
derive it. If it records a decision, store it — and still validate it at the
boundary.

The second principle: **insights must be statements, not estimates.** Every line is
a deterministic function of the log, and the suite cross-checks each one against an
independent hand computation — the top category names the hand-computed largest
category *and* its money total; the heaviest day names the hand-computed weekday;
the average-day line carries the hand-computed per-day figure; the largest-expense
line names the hand-computed largest label. A regex also asserts no insight contains
"might", "could", "probably", "estimate" or "perhaps".

### Bugs found and fixed
1. **`Derive.money` did not round, so divisions leaked their tail.** The Insights
   view read "An average day this month has cost **₹1,740.769**". `fmt()` is a
   general number formatter and `toLocaleString` happily emits three decimals; a sum
   of two-decimal amounts would leak `₹13,130.000000000002`. `money()` now rounds to
   paise before formatting. **Found by looking at a screenshot, not by a suite** —
   every money figure until then happened to be whole, so no assertion caught it.
   This is exactly why POLISH is a separate step from TEST.
2. **A figure was mislabelled as something it was not.** The month summary strip said
   "Avg / day" but computed `expenses / rowCount` — an average *transaction*.
   `financeTotals` now exposes `perTransaction` and `financeMonth` adds a genuine
   `avgPerDay` divided by **elapsed** days (a day that has not happened yet has not
   been spent on), and the suite asserts the two are different figures.

### Test-side fixes (stale expectations, not app defects)
- **The demo's generated log already had one category over budget.** So "deleting the
  probe returns `overCount` to 0" failed against correct behaviour. The cascade now
  baselines against the real position first (`base.overCount`, `base.overBy`) and
  asserts the *delta* — the same discipline as deriving expectations from `State`
  instead of hardcoding demo data. The test also picks a target just above what was
  already spent, so the budget starts green and the probe is what tips it over.
- **A contrast assertion was too narrow.** `/^rgb\((1[0-9]|[0-7][0-9]),/` accepts only
  very dark reds; the muted grey-blue `rgb(86,94,124)` on a light surface is correct
  and failed it. Replaced with perceived luminance
  (`0.2126r + 0.7152g + 0.0722b < 140`).
- **Two counts included an element they should not have.** "Five view tabs" counted 6
  because the aside's "Open budgets" shortcut legitimately carries the same
  `data-fin-view` attribute; scoped to `.fin-tools .viewtabs`. A harness crash
  (`topMoney is not defined`) was a bare name I had used as if it were a variable.
- **t27's schema assertions legitimately grew** — the singleton now holds `budgets`
  as well as `currency`, so the "preferences only" check became an allow-list rather
